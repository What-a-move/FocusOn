# FocusOn Streamlit 유사도 실험 구현·평가 지침 — Qwen3-Embedding-4B

- 작성 기준일: 2026-10-03
- 산출물: 이 MD 한 개. 학교 컴퓨터에서 구현·실행·평가할 작업 명세다.
- 지정 모델: **Qwen/Qwen3-Embedding-4B**.
- 실행 환경: 학교의 RTX A4000 / 시스템 RAM 128 GB. 이 문서를 작성하면서 해당 환경에서 Qwen3-Embedding-4B를 실행하거나 정확도를 측정하지 않았다.
- 현재 코드·기존 ZIP: 이전 임베딩 후보와 제한된 Graph를 사용한다. **이 MD를 저장했다고 기존 코드나 ZIP이 Qwen3 버전으로 바뀐 것은 아니다.** 아래 변경과 학교 검증을 완료해야 한다.

## 1. 기준과 범위

[Notion 유사도 검색](https://app.notion.com/p/3e1357537c3180b7a519f8c7940c80d2)의 1~7번 방법을 동일 입력으로 비교한다. 8번은 목표 개념 확장 전략이므로 독립적인 점수 방식으로 표시하지 않는다. [Notion 학습 목표와 콘텐츠 관련성 판단](https://app.notion.com/p/3e1357537c31807ba146ebda318f025a)은 6번 Hybrid를 MVP 1차 판단으로 설명하지만, 이 실험에서 다른 방법의 실제 결과와 함께 검증한다.

사용자가 요청한 입력은 학습 목표와 이미 추출된 DOM/OCR 텍스트다. 이 실험 화면은 DOM 수집이나 OCR 엔진을 실행하지 않는다. 카메라·원본 이미지·체류 시간·알림·차단 기능은 구현 범위에 포함하지 않는다. 현재 콘텐츠의 관련성만 평가하며, 한 번의 UNRELATED를 사용자 이탈 확정으로 표현하지 않는다.

Notion에 확정 임계값·결합 가중치·정확도 보증 수치는 없다. 이 문서의 초기 자원 설정과 판정 후보 규칙은 실험 제안이며 개발 데이터로 검증해야 한다. 개인정보·실패 처리에는 기존 AI-PRIV-002, AI-FAIL-001, AI-REL-001을 적용한다.

## 2. Streamlit 화면 요구사항

두 개의 주요 입력 칸을 만든다.

1. **학습 목표**: 사용자가 입력하는 문장. 기존 GoalProfile 또는 기존 더미의 goal JSON도 같은 칸에서 허용한다.
2. **DOM/OCR 추출 텍스트**: 한 입력 영역에 이미 추출된 텍스트를 붙여넣는다. 출처 선택 버튼을 DOM / Chrome 화면 OCR / Desktop OCR로 두고 현재 선택을 입력 칸 제목에 표시한다. JSON 입력도 같은 영역에서 받는다.

출처는 기존 contentSource 값 CHROME_DOM / CHROME_VIEWPORT_OCR / DESKTOP_APP_OCR로 매핑한다. 모든 텍스트 영역과 방법 선택은 [Streamlit form](https://docs.streamlit.io/develop/api-reference/execution-flow/st.form) 안에 둔다. 입력 중에는 채점하지 않고 **선택한 방식 비교** 버튼을 눌렀을 때만 계산한다.

방법 1~7번을 번호와 이름으로 모두 보여 주고 복수 선택·전체 선택·전체 해제를 지원한다. 사용자가 선택한 방법만 실행한다. 7번은 별도 reranker가 필요한 점과 현재 준비 상태를 방법 이름 옆에 표시한다.

추가 접힘 영역은 다음만 제공한다.

- 목표 개념 확인: 직접·보조·선수 개념, 동의어와 Graph 관계를 보여 주고 사용자가 확인한다.
- 입력 JSON 예시와 DOM/OCR 출처 설명.
- 학교 모델 준비 상태, 모델 ID·리비전, 장치·dtype, 보정 설정의 유무.
- 합성 정답 세트를 이용한 평가 결과. 한 입력의 원점수와 데이터셋 정확도는 별도 화면 항목으로 표시한다.

목표나 콘텐츠를 바꾸면 이전 결과를 숨기거나 이전 입력 결과임을 명확히 표시한다. 모델 로드 실패·추론 실패가 발생한 뒤에도 이전 결과를 현재 결과처럼 유지하지 않는다.

## 3. 기존 입력 형식 유지

제품 요청 JSON이나 API 응답에 새 컬럼을 추가하지 않는다. 방법별 원점수·Graph 경로·실행 시간·보정 상태는 **실험 화면과 평가 설정에만** 둔다. 아래의 기존 필드는 입력 예시이며 최종 제품 계약을 새로 선언하는 것이 아니다.

목표 칸의 기존 GoalProfile 예시:

~~~json
{
  "mainTopic": "파인튜닝 학습",
  "coreTopics": ["Fine-tuning", "LoRA", "PEFT"],
  "supportingTopics": ["Transformer", "선형대수", "행렬", "벡터"]
}
~~~

기존 더미 형식인 text / directTerms / supportTerms도 호환 입력으로 받을 수 있다. 사용자가 일반 문장만 넣었다면 GoalProfile이 완성됐다고 가정하지 않는다. 사람이 확인한 목표별 템플릿을 선택·검토하거나 같은 목표 칸에 GoalProfile JSON을 넣게 한다. 방문 페이지·정답 라벨을 읽고 목표 개념을 확장하지 않는다.

콘텐츠 칸은 다음 형태를 허용한다.

- 추출 텍스트만 입력: 출처 선택값을 사용한다. 실제 추출 성공·OCR 품질을 측정한 입력으로 간주하지 않는다.
- 기존 pageTitle / text / contentSource / extractionStatus JSON.
- 기존 passages 배열: 문단의 id·kind·order와 출처 범위를 유지한다. 배열을 단순 문자열로 합쳐 코드·표·OCR 구분을 버리지 않는다.
- 기존 합성 cases 배열: 정답 메타데이터를 제거한 입력만 계산 함수에 전달한다.

OCR 품질값이 제공되면 기존 qualityScore를 검사한다. 제공되지 않았는데 실제 품질이 1.0이라고 표시하지 않는다. 합성 텍스트로 품질을 가정하는 실행은 화면에 **추출 품질 미검증**으로 표시한다. 품질 확인이 필요한 사례는 원점수를 조사할 수 있어도 최종 판정은 UNCERTAIN으로 둔다.

추출 FAILED/UNSUPPORTED, 빈 콘텐츠, 읽을 수 없는 OCR, 제외·민감 데이터는 모델 호출 전에 처리한다. EXCLUDED와 PRIVACY_BLOCKED는 해당 공개 라벨을 유지하고 원점수를 비워 둔다. 실패·품질 부족은 UNCERTAIN이며 UNRELATED가 아니다.

## 4. 목표 개념과 작은 Graph

Notion에 있는 관계는 다음과 같다.

~~~text
Fine-tuning
├─ DIRECT: LoRA, PEFT
├─ SUPPORTING: Transformer, Optimization
└─ PREREQUISITE: Linear Algebra
   ├─ Matrix
   └─ Vector
~~~

이 관계는 목표별 **실험 템플릿 설정**으로 관리하고 사용자가 목표를 확정할 때 확인한다. 기존 GoalProfile에 prerequisiteTopics 같은 새 필드를 임의로 추가하지 않는다. supportingTopics 배열만으로 SUPPORTING과 PREREQUISITE를 추정하지 않는다. 관계가 명시된 템플릿이 없으면 관계 미정으로 남긴다.

각 개념에는 사람이 확인한 대표 이름과 동의어를 둔다. 개념별 임베딩은 대표 개념을 사용하고, 동의어는 키워드 검색에 사용한다. 같은 개념의 여러 동의어 적중을 여러 개념의 적중으로 부풀리지 않는다.

목표 변경 시 Graph·목표 임베딩·판정 설정의 적용 범위를 다시 확인한다. 같은 비교 실행에서 모든 방법에 같은 확정 목표와 같은 콘텐츠 문단을 넣는다. 2·4·5·6·7번에 필요한 확장 개념 또는 관계가 없으면 **부분 실행 또는 NOT_RUN** 이유를 표시한다. 단순 목표 문자열만으로 전체 Graph 방식이 구현됐다고 표시하지 않는다.

## 5. Qwen3-Embedding-4B 적용

공식 [Qwen3-Embedding-4B 모델 카드](https://huggingface.co/Qwen/Qwen3-Embedding-4B)와 [Qwen 공식 사용 예제](https://github.com/QwenLM/Qwen3-Embedding)를 기준으로 사용한다. 이 모델은 텍스트 임베딩 모델이며, 최대 임베딩 차원은 2560이다. 임베딩 모델이 판정 이유 문장을 생성하거나 reranker 역할까지 수행한다고 가정하지 않는다.

학교 구현에서 다음을 고정한다.

- 3·4·6번 및 7번의 임베딩 단계에 같은 모델 ID와 같은 리비전을 사용한다.
- 목표·개념 질의에는 고정된 영어 작업 지시문을 사용한다. 콘텐츠 문단에는 같은 질의 지시문을 붙이지 않는다.
- 이전 E5용 query: / passage: 접두사를 그대로 재사용하지 않는다.
- Sentence Transformers 모델에 포함된 pooling을 사용한다. Transformers를 직접 쓸 경우 공식 last-token pooling과 정규화 예제를 따르며 임의 mean pooling으로 바꾸지 않는다.
- 정규화한 벡터의 내적으로 코사인을 계산한다. 원점수를 임의로 0~1로 자르거나 100을 곱해 정확도로 표시하지 않는다.
- 리비전, 지시문, 출력 차원, dtype, 문단 분할 방식, 토큰 상한을 평가 설정에 기록한다. 리비전·지시문·양자화가 바뀌면 기존 임계값을 재사용하지 않는다.

초기 작업 지시문은 다음을 사용하고, 변경은 개발 세트에서만 평가한다.

~~~text
Given a confirmed learning goal, retrieve passages about the goal or supporting knowledge necessary to achieve it.
~~~

아래는 학교에서 모델 적재와 원점수 계산을 확인하기 위한 예시다. 이 코드의 실행 성공은 관련성 판정의 정확도를 입증하지 않는다. 최초 출력된 리비전을 저장하고 후속 비교에는 그 값을 고정한다.

~~~python
import numpy as np
import torch
from huggingface_hub import HfApi
from sentence_transformers import SentenceTransformer

MODEL_ID = "Qwen/Qwen3-Embedding-4B"
if not torch.cuda.is_available():
    raise RuntimeError("학교 GPU 실행을 확인하지 못했습니다.")

revision = HfApi().model_info(MODEL_ID).sha
dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
model = SentenceTransformer(
    MODEL_ID,
    revision=revision,
    device="cuda",
    model_kwargs={"torch_dtype": dtype, "attn_implementation": "sdpa"},
    tokenizer_kwargs={"padding_side": "left"},
)
model.max_seq_length = 1024  # 초기 실험값. 토큰 초과는 분할·기록한다.
prompt = (
    "Instruct: Given a confirmed learning goal, retrieve passages about "
    "the goal or supporting knowledge necessary to achieve it.\nQuery: "
)
queries = ["파인튜닝 학습"]
documents = [
    "LoRA 어댑터를 이용해 언어 모델을 미세조정하는 실습입니다.",
    "레이싱 게임에서 차량을 선택하고 랩타임 기록을 확인합니다.",
]
q = model.encode(
    queries, prompt=prompt, batch_size=1,
    normalize_embeddings=True, show_progress_bar=False,
)
d = model.encode(
    documents, prompt="", batch_size=1,
    normalize_embeddings=True, show_progress_bar=False,
)
scores = q @ d.T
assert q.shape[1] == d.shape[1] == 2560
assert np.isfinite(scores).all()
print("model:", MODEL_ID, "revision:", revision, "dtype:", dtype)
print("raw_cosine:", scores.tolist())
~~~

벡터 수·차원·유한값·정규화를 검사한다. 실패 시 ANALYSIS_UNAVAILABLE 사유와 UNCERTAIN으로 처리하며 0점이나 임의 대역 점수를 생성하지 않는다. Streamlit에서는 모델 객체만 cache_resource로 재사용한다. 입력 원문·결과 문단을 전역 캐시에 저장하지 않는다.

7번은 별도 reranker 모델이 필요하다. 사용자가 지정한 것은 임베딩 모델이므로 reranker는 아직 확정하지 않는다. 별도 실험 후보로 [Qwen3-Reranker-0.6B](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)를 검토할 수 있다. 선택하지 않았거나 적재 실패 시 7번은 NOT_RUN이다. 이 모델을 선택하면 공식 전용 입력 형식과 yes/no 토큰 점수 계산을 사용하고, 일반 CrossEncoder 인터페이스를 그대로 적용할 수 있다고 가정하지 않는다. 그 점수도 FocusOn 판정의 보정된 정답 확률이 아니다.

## 6. 방법별 실제 계산과 한계

키워드 수, 코사인, reranker 점수는 서로 다른 척도다. 값의 크기로 방법 간 우열을 정하지 않는다.

| 번호 | 계산 | 화면에 보여 줄 근거 | 판정 한계 |
| --- | --- | --- | --- |
| 1 단순 키워드 | 목표의 고정 기본 키워드를 제목·문단에서 검색. 서로 다른 개념 적중 수를 기록 | 적중 개념·원래 문단 ID·문단 텍스트 | 표현 차이·선수 지식을 놓침. 미적중으로 UNRELATED 금지 |
| 2 확장 키워드 | 확인된 동의어와 직접·보조·선수 개념 그룹으로 검색 | 그룹별 적중 개념·근거 문단. 단어만 찾은 것인지 관계도 확인됐는지 표시 | 템플릿·동의어가 없으면 부분 실행. 넓은 단어 한 번만으로 RELATED 금지 |
| 3 단일 목표 임베딩 | 목표 전체 질의 1개 × 모든 문단의 Qwen 코사인 행렬 | 문단별 코사인과 상위 근거. 최고값은 후보 탐색용으로만 표시 | 낮은 값만으로 UNRELATED 금지. 최고 문단 하나로 페이지 전체 판정 금지 |
| 4 다중 개념 임베딩 | 직접·보조·선수 대표 개념마다 Qwen 임베딩, 문단별 비교 | 개념·관계·문단별 코사인, 그룹별 분포 | 관계 확인이 없는 가장 높은 개념 하나를 정상 학습으로 확정하지 않음 |
| 5 작은 Graph + 키워드 | 키워드에 맞은 개념의 목표까지 경로와 관계를 조회 | 실제 DIRECT/SUPPORTING/PREREQUISITE 경로와 문단 | 2번 함수만 재사용하고 Graph 구현이라고 부르지 않음. 관계 미정·Graph 미적중은 보류 |
| 6 Graph + 키워드 + 임베딩 | 같은 개념의 키워드 적중·코사인·Graph 관계를 결합 | 키워드와 의미 근거가 같은 문단을 지지하는지, 충돌하는지 | 결합식·가중치·임계값이 없으면 개별 신호만 표시하고 판정 보류. 임의 0.55/0.45 금지 |
| 7 Hybrid + 재정렬 | 6번이 모호하거나 근거 충돌인 경우에만 목표·후보 문단 쌍을 rerank | 6번 근거, 재정렬 전후 순위, reranker 원점수, 호출 사유 | 모델 미준비는 NOT_RUN. 높은/낮은 reranker 점수 단독으로 최종 판정 금지 |

1번의 기본 목록과 2번의 확장 목록을 별도로 고정해 실제 차이를 비교한다. 2·5번이 같은 개념 집합을 쓰면 결과가 같을 수 있으며 성능 향상을 꾸며 내지 않는다. 6번의 결합식은 먼저 키워드·의미·관계 신호를 별도로 기록한 뒤 개발 세트에서 정한다. 7번 보류 구간이 아직 보정되지 않았다면 선택한 판단 가능 사례를 경계 사례로 처리할 수 있지만, 이 실험 조건과 실제 호출률을 반드시 기록한다.

8번은 **목표 확장 조건**으로 따로 비교한다. 초기에는 사람이 검토한 템플릿을 사용한다. LLM 자동 확장은 이 요청의 필수 구현이 아니며 페이지마다 호출하지 않는다.

## 7. 원점수와 relevanceLabel 분리

계산 결과와 최종 판정은 별도 단계로 구현한다.

~~~text
입력 검증·전처리
  → 선택 방식의 원점수·관계·문단 근거 계산
  → 해당 방식의 보정 설정 및 근거 조건 확인
  → relevanceLabel + reasonCode + reason + evidenceIds
~~~

원점수 0.86을 86% 신뢰도라고 쓰지 않는다. 보정된 판정 설정이 없으면 **실제 모델 원점수는 표시하되 relevanceLabel=UNCERTAIN**으로 둔다. 이 원칙은 임의 두 문단 적중 규칙을 포함한 미검증 키워드 규칙에도 적용한다. 실험 후보가 RELATED/SUPPORTING으로 보이는 것과 검증된 최종 RELATED를 분리한다.

방법별 정책은 다음 조건을 사용한다.

- **RELATED**: 품질이 충분하고 확정 목표의 직접 수행 또는 필요한 보조·선수 관계가 현재 근거에서 확인된다. 해당 방식·모델·출처의 개발 세트에서 정한 기준을 충족하고 충돌이 없다. SUPPORTING/PREREQUISITE는 최종 RELATED에 포함한다.
- **UNRELATED**: 품질이 충분한 제목과 대표 본문/OCR이 동일한 다른 활동을 명확하게 설명하고, 직접·보조·선수 관계가 없으며, 충돌이 없고, 해당 방식의 검증된 무관 기준을 충족한다.
- **UNCERTAIN**: 임계값 미설정, 제목·본문 충돌, 관계 미확인, 추출 품질 부족, 정보 부족, 모델 실패, 낮은 점수만 있고 명시적인 다른 활동 근거가 없는 경우.
- **EXCLUDED / PRIVACY_BLOCKED**: 원점수와 판정 추론을 실행하지 않는다.

1~5번은 낮은 점수나 미적중만으로 UNRELATED를 확정할 능력이 부족하다. 보류를 유지한다. 6·7번도 명시적인 다른 활동 근거 추출 규칙과 무관 기준이 구현·평가되지 않았다면 UNRELATED를 반환하지 않는다. 모든 방법에서 억지로 같은 이진 결과를 내게 하지 않는다.

게임 활동 근거를 확인하는 실험 규칙을 만들 경우, 목표와 콘텐츠 양쪽을 고려하고 제목·본문에 일관된 게임 플레이 근거가 있는지 확인한다. '게임'이라는 단어나 사이트 주소만으로 무관 판정하지 않는다. 게임 개발·게임 AI·게임 분석 목표에서는 동일 화면이 관련 자료일 수 있다. 해당 규칙은 Notion에 확정된 분류기로 적힌 내용이 아니므로 제안 규칙으로 표시하고 별도 오판 사례로 검증한다.

T3_related, T4_direct, T4_support, T6_related, T6_off, T7_related 등의 설정은 초기에는 미설정이다. 개발 세트에서 방식·모델 리비전·문단 처리·출처별 점수 분포를 보고 정한다. DOM과 OCR을 함께 쓴 임계값이 OCR 오판을 늘리는지 확인하고, 출처별 기준이 필요하면 별도 개발 검증을 거친다. 임계값의 구체적 숫자를 더미 두 사례에 맞춰 만들지 않는다.

## 8. 결과 화면과 반환 문구

방법마다 별도 행을 만들고 다음을 표시한다. 아래 항목은 **실험 화면 열**이며 제품 JSON 컬럼 추가 목록이 아니다.

| 항목 | 표시 내용 |
| --- | --- |
| 방법·실행 상태 | 번호·이름, 실행 완료 / 부분 실행 / NOT_RUN / SKIPPED / 오류 |
| 출처·품질 | DOM/OCR, 추출 상태, 품질 검증 여부 |
| 원점수와 종류 | 키워드 적중 수 / 코사인 / 결합 신호 / reranker 점수. 없는 값은 빈 값 |
| 실험 후보 | 직접·보조·선수·무관 후보 또는 UNKNOWN. 최종 라벨과 구분 |
| relevanceLabel | RELATED / UNRELATED / UNCERTAIN / EXCLUDED / PRIVACY_BLOCKED |
| reasonCode·reason | 현재 입력에 근거한 판정·보류·실패 이유 |
| 근거 | evidenceIds, 입력에서 실제로 나온 근거 문단 텍스트, 개념·관계 경로 |
| 시간 | 전처리·목표 준비·콘텐츠 임베딩·규칙·재정렬·전체 시간을 구분 |
| 보정 상태 | 미보정 / 개발 세트 보정 완료 / 고정 테스트 평가 완료와 설정 버전 |

문단별 상세 표에는 개념 이름·관계·문단 ID·텍스트·원점수를 표시한다. 중첩 청크 두 개를 독립 근거 두 개로 세지 않는다. 원래 같은 제목이나 문단에서 나온 중복 근거도 중복 제거한다. 충분한 독립 근거가 없으면 한 문단의 최고점으로 페이지 전체를 확정하지 않는다.

기존 출력 필드 relevanceLabel / reasonCode / reason / evidenceIds를 사용한다. contentRole, confidenceLevel 등 Notion 제안 필드와 로컬 API 초안의 차이는 그대로 계약 검토 대상으로 남긴다. 이 문서에서 제품 응답 필드를 새로 확정하지 않는다. 입력·정답·근거를 분리하고 원점수를 기존 confidence에 복사하지 않는다.

반환 텍스트는 입력 문단과 확인된 관계를 이용하는 고정 템플릿으로 만든다. Qwen 임베딩 모델에 이유 문장 생성을 요구하지 않는다.

| 조건 | 반환 텍스트 예시 |
| --- | --- |
| 직접 RELATED | 현재 제목과 본문에서 LoRA 실습이 확인되어 파인튜닝 목표의 직접 학습 자료로 판단했습니다. |
| 보조 RELATED | 현재 문단은 행렬 연산을 설명하며, 확정 목표 Graph에 필요한 선수 지식으로 연결되어 있습니다. |
| 검증된 UNRELATED | 현재 제목과 본문은 레이싱 게임 플레이를 설명합니다. 확정 목표의 직접·보조 관계를 확인하지 못했고 검증된 무관 기준을 충족했습니다. |
| 미보정 UNCERTAIN | 실제 Qwen 임베딩 점수를 계산했지만 이 방식의 판정 기준이 아직 검증되지 않아 판단을 보류합니다. |
| 품질 부족 UNCERTAIN | OCR 텍스트의 품질이나 문맥을 확인하기 어려워 목표와의 관계를 판단하지 않았습니다. |

위 문구는 결과 형식 예시이지 측정된 결과가 아니다. '사용자가 집중하지 않았다', '게임을 하다가 이탈했다'처럼 현재 텍스트가 입증하지 못하는 행동을 추측하지 않는다. 민감정보가 포함된 문단은 근거로 재출력하지 않는다. 합성 입력 문단은 세션 화면에 표시할 수 있지만 실제 사용자 원문을 파일·로그·전역 캐시에 저장하지 않는다.

## 9. 화면 확인용 합성 사례

목표는 '파인튜닝 학습'으로 고정하고 위 GoalProfile·사용자 확인 템플릿을 사용한다. 정답은 **평가 메타데이터**이며 아래 분석 입력에 포함하지 않는다.

RELATED 기대 사례의 DOM 입력:

~~~json
{
  "pageTitle": "LoRA로 언어 모델 파인튜닝하기",
  "text": "LoRA 어댑터를 적용해 언어 모델을 미세조정합니다. PEFT 설정, 학습 데이터 구성, 파인튜닝 결과 확인 과정을 실습합니다.",
  "contentSource": "CHROME_DOM",
  "extractionStatus": "SUCCESS"
}
~~~

UNRELATED 기대 사례의 OCR 입력:

~~~json
{
  "pageTitle": "온라인 레이싱 게임 플레이",
  "text": "레이싱 게임에 접속해 차량을 선택하고 실시간 대전에 참가합니다. 랩타임 기록과 아이템 보상을 확인하며 게임 플레이를 계속합니다.",
  "contentSource": "CHROME_VIEWPORT_OCR",
  "extractionStatus": "SUCCESS",
  "qualityScore": 0.95
}
~~~

OCR의 0.95는 합성 예시 값이며 실제 OCR 인식 결과가 아니다. 두 사례는 화면·모델 호출 확인에만 사용한다. 보정 전에는 기대 정답이 UNRELATED여도 계산 결과는 UNCERTAIN일 수 있다. 기대 정답을 결과에 복사하거나 실패한 모델 점수를 조작해 기대 라벨을 맞추지 않는다.

같은 학습·게임 내용을 DOM/OCR 양쪽으로 바꿔 교차 검사한다. 위 두 사례만 비교하면 활동 종류와 추출 출처가 함께 바뀌어 출처 성능을 평가할 수 없다. 추가로 선수 지식, 코드 오류 해결, 목표 단어가 광고에만 등장하는 게임 페이지, OCR 깨짐, 제목·본문 충돌, 짧은 코드, 목표가 게임 개발인 사례를 포함한다.

## 10. 학교에서 신뢰성을 평가하는 절차

1. **정답 준비**: 모델 점수 보기 전에 목표·콘텐츠·근거를 사람이 검수해 RELATED / UNRELATED / UNCERTAIN 정답을 정한다. 보조·선수 자료가 왜 필요한지도 확인한다. 개인정보가 없는 합성 자료만 저장한다.
2. **분할**: 개발 세트와 최종 고정 테스트 세트를 문서·영상·연속 캡처·목표 기준으로 분리한다. 같은 원문의 DOM과 OCR, 문장만 바꾼 사례를 서로 다른 분할에 넣지 않는다. 일부 목표 전체를 테스트에 남긴다.
3. **구성**: 직접 학습·보조·선수·다른 활동·모호함·실패를 넣고 한국어·영어·코드·OCR 오류를 포함한다. 기존 10개 목표 × 약 20개 활동 제안은 파일럿 규모이며 품질 보증 수량이 아니다.
4. **개발 평가**: 개발 세트에서만 템플릿·동의어·Graph·임계값·결합식·보류 구간을 선택한다. 정답 라벨은 계산 함수의 인자로 전달하지 않는다.
5. **고정 평가**: 모델 리비전·모든 설정을 고정한 뒤 보지 않은 테스트 세트를 실행한다. 테스트 결과를 보고 수정했다면 기존 테스트는 개발 자료가 되므로 새 고정 세트로 다시 검증한다.
6. **방법 비교**: 같은 사례에서 혼동행렬, 라벨별 Precision/Recall/F1, Macro F1, 보류율, 정상 학습·보조 학습을 UNRELATED로 오판한 수와 비율, 무관을 놓친 수를 비교한다.
7. **속도 비교**: 모델·목표 준비 시간을 별도로 기록한다. 목표 캐시는 준비된 상태, 콘텐츠 캐시는 미적중인 조건으로 각 방법을 비교한다. GPU 동기화 후 시간과 VRAM을 측정한다. 초기 워밍업 5회·반복 30회는 지연 측정을 위한 제안이지 정확도 표본 추가가 아니다.
8. **선택**: 정상·보조 활동의 잘못된 UNRELATED를 우선 확인하고, 보류율·라벨별 성능·P50/P95 지연을 함께 비교한다. 목표 성능·허용 오판율·지연 예산이 정해지지 않았다면 임의로 합격 선언하지 않는다.

UNCERTAIN 예측을 빼고 정확도만 높게 보고하지 않는다. 2개 정답 라벨로 평가하는 세트라면 보류는 정확도 계산에서 맞춘 사례가 아니며, 판단한 사례만의 정확도를 별도로 보고할 때는 반드시 판단 비율도 같이 표시한다. 의미적 UNCERTAIN 정답이 있는 세트는 3개 라벨 평가와 보류 원인도 보고한다. 제외·추출 실패는 의미 관련성 성능 집계와 분리하고 실패율을 별도로 보고한다.

여러 방법 비교에서 콘텐츠 임베딩을 공통으로 한 번 생성해 재사용할 수 있다. 화면에는 그 공통 준비 시간을 명시한다. 이미 계산된 임베딩을 사용한 4·6번의 후속 연산 시간만 보고 전체 방법이 더 빠르다고 주장하지 않는다. 성능 비교에는 각 방법에 필요한 임베딩 비용을 포함하거나 모든 방법에 동일한 캐시 조건을 적용한다.

각 결과는 다음 상태로 구분한다.

| 상태 | 의미 |
| --- | --- |
| 실제 추론 확인 | 지정 Qwen 리비전의 실제 벡터·점수가 반환됨. 판정 정확도는 아직 미검증 |
| 개발 기준 보정 | 개발 데이터로 방법별 기준을 정함. 최종 성능은 아직 미검증 |
| 고정 테스트 평가 완료 | 미사용 테스트 세트의 성능·오판·보류·지연을 실제로 기록함 |
| 사용 승인 여부 미정 | 실측은 있지만 팀의 허용 오판·속도 기준이 아직 결정되지 않음 |

결과 보고에는 GPU·VRAM·RAM·OS·드라이버·PyTorch·라이브러리 버전, 모델 리비전·지시문·dtype·토큰 상한, 데이터 분할·라벨별 사례 수·설정 버전과 실제 지표를 남긴다. 비어 있는 지표를 추정값으로 채우지 않는다.

## 11. RTX A4000 준비와 메모리 확인

[NVIDIA의 RTX A4000 사양](https://www.nvidia.com/en-us/products/workstations/rtx-a4000/)은 VRAM 16 GB다. 사용자가 말한 128 GB는 시스템 RAM이다. 실제 학교 장치 이름과 남은 VRAM은 nvidia-smi로 확인한다. 4B의 16비트 가중치만 단순 계산하면 약 8 GB 규모이지만, 실행에는 활성값·버퍼·다른 프로그램 메모리도 필요하므로 적재·속도를 보장하지 않는다.

초기 실험은 batch_size=1, max_seq_length=1024, 출력 2560차원, BF16 지원 확인 후 BF16 또는 FP16으로 시작한다. 모두 자원 확인을 위한 초기 설정이다. 토큰 초과 입력은 출처 범위를 보존해 나누고, 잘린 입력을 전체 문서로 판정하지 않는다. FlashAttention은 선택 최적화이며 설치 성공을 필수 시작 조건으로 만들지 않는다.

OOM이 발생하면 NOT_RUN/오류로 표시하고 배치·토큰·동시 모델 적재 상태를 확인한다. reranker를 포함한 동시 적재가 불가능하면 순차 적재 조건을 기록한다. 모델을 더 작은 것으로 바꾸거나 CPU로 옮겨 놓고 같은 GPU 모델의 성공 결과라고 표시하지 않는다. dtype·양자화를 변경한 결과는 별도 실험 조건으로 평가한다.

아래 준비는 학교에서 수행한다. 집에서는 Qwen 가중치를 다운로드하거나 실행할 필요가 없다.

~~~bash
nvidia-smi
python --version
python -m venv .venv
~~~

가상환경 활성화는 운영체제에 맞게 수행한다. Linux는 source .venv/bin/activate, Windows PowerShell은 .venv\Scripts\Activate.ps1을 사용한다. [PyTorch 공식 설치 선택기](https://pytorch.org/get-started/locally/)에서 해당 운영체제·드라이버에 맞는 CUDA 패키지를 먼저 설치한다. 임의 CUDA 버전을 이 문서에서 고정하지 않는다.

~~~bash
python -m pip install "streamlit>=1.40,<2" "transformers>=4.51,<5" "sentence-transformers>=5,<6" accelerate huggingface-hub pytest
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'NO_CUDA')"
~~~

transformers 최소 지원 조건은 공식 Qwen 예제에 근거한다. 설치 후 실제 버전을 기록·고정한다. 위는 준비 명령이며 현재 집 환경에서 Qwen4B 실행 검증을 완료했다는 뜻이 아니다.

## 12. 기존 코드에서 바꿀 작업과 완료 조건

대상은 기존 AI/evaluation/similarity_streamlit.py, similarity_methods.py, requirements-streamlit.txt 및 해당 평가 테스트다. 전처리는 실제 필요한 입력 검증·문단 출처 보존 부분만 변경한다. 모델을 이름만 Qwen으로 바꾸지 말고 목표 질의와 콘텐츠 문서를 별도 encode하는 Adapter로 수정한다.

구현 순서:

1. 이 MD의 입력·출력·실험 상태를 먼저 적용한다.
2. Qwen4B 리비전 고정 로더와 위 모델 단독 확인을 학교 GPU에서 수행한다.
3. 1·2번 키워드 목록을 구분하고, 4번 개념별 코사인 표와 5번의 실제 관계 경로를 구현한다.
4. 6번의 개별 신호·근거 충돌·결합 설정과 7번의 모호 사례 호출 조건을 구현한다. 준비되지 않은 방법은 NOT_RUN으로 표시한다.
5. 점수 함수가 최종 라벨을 직접 반환하지 않도록 판정 함수를 분리한다. 보정 설정이 없으면 UNCERTAIN을 반환한다.
6. 근거 ID·실제 문단 텍스트·판정 이유·보정 상태·전체 시간을 화면에 표시한다.
7. 합성 데이터·개발/테스트 분할로 평가하고 결과를 기록한다.

Qwen 적용 후 실행할 기존 진입점:

~~~bash
python -m streamlit run AI/evaluation/similarity_streamlit.py
~~~

현재 코드로 위 명령을 실행했다고 지정 Qwen 모델이 사용되는 것은 아니다. Qwen 로더·입력 Adapter가 반영되고 화면의 모델 ID·리비전을 확인해야 한다.

학교 작업 완료 체크리스트:

- [ ] 목표 입력 칸과 DOM/OCR 출처 선택이 있는 콘텐츠 입력 칸이 동작한다.
- [ ] 선택한 방법만 버튼으로 실행하고 이전 입력 결과를 잘못 유지하지 않는다.
- [ ] 실제 Qwen3-Embedding-4B 리비전·CUDA·dtype·벡터 차원을 확인했다.
- [ ] 질의 지시문·문서 입력·정규화가 공식 사용법에 맞는다.
- [ ] 목표 템플릿·Graph를 사용자가 확인했고 입력 콘텐츠나 정답으로 확장하지 않았다.
- [ ] 1·2·4·5번의 계산 차이와 근거가 화면에 확인된다.
- [ ] 선수 관계가 없는 입력을 전체 Graph 구현으로 표시하지 않는다.
- [ ] 원점수·실험 후보·relevanceLabel·판정 이유·근거 문단을 구분한다.
- [ ] 미보정·실패·부족한 OCR 근거가 UNRELATED로 바뀌지 않는다.
- [ ] 실제 추출 실패·민감·제외 입력에서는 점수와 근거 원문을 출력하지 않는다.
- [ ] 정답을 바꿔도 같은 입력의 원점수·예측은 바뀌지 않는 테스트를 통과한다.
- [ ] 중첩·중복 문단을 독립 근거로 부풀리지 않는 테스트를 통과한다.
- [ ] 모델 실패·OOM·임계값 미설정·제목/본문 충돌이 적절히 보류된다.
- [ ] 학습·게임·선수·코드 사례를 DOM/OCR 양쪽으로 평가했다.
- [ ] 별도 고정 테스트의 성능·오판·보류율과 RTX A4000 P50/P95를 실제 기록했다.
- [ ] 고정 테스트 결과와 허용 오판·지연 기준을 확인한 뒤 방법을 선택했다.

## 13. 학교 구현 담당자에게 전달할 작업 지시

> 이 MD를 기준으로 FocusOn의 로컬 Streamlit 관련성 평가 도구만 수정한다. 주요 입력은 학습 목표와 DOM/OCR 추출 텍스트이며, 사용자가 방법 1~7번을 선택해 버튼으로 실행한다. 임베딩 모델은 Qwen/Qwen3-Embedding-4B로 지정하고 공식 질의 지시문·문서 인코딩·정규화·리비전 고정을 적용한다. 기존 입력 JSON과 제품 API 컬럼을 임의로 늘리지 않는다. 원점수 계산과 relevanceLabel 판정을 분리하고 실제 근거 문단·판정 이유·보정 상태·실행 시간을 표시한다. 모델이나 필요한 관계가 없는 방식은 NOT_RUN 또는 부분 실행으로 표시한다. 판정 기준은 개발 세트에서 정하고 별도 고정 테스트로 검증한다. 낮은 코사인·키워드 미적중·추출 실패만으로 UNRELATED를 만들지 않는다. 현재 ZIP의 코드가 이 명세를 이미 충족한다고 가정하지 말고 구현 차이를 확인한다. 검증 결과를 실제 측정값으로 기록하고 필요한 테스트를 통과한 뒤 완료 상태를 보고한다.

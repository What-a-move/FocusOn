# 사용자 피드백·개인화 명세

## 문서 상태

- 상태: 팀 검토용 계약 초안, 미구현
- 버전: `0.1.0`
- 기준일: 2026-09-12
- 관련 Issue: [#3](https://github.com/What-a-move/FocusOn/issues/3)
- 관련 규칙: `AI-FEEDBACK-001`, `AI-CACHE-001`, `AI-STALE-001`, `AI-ACTION-001`, `AI-PRIV-002`

이 문서는 사용자의 수정·선택을 어떤 의미로 저장하고 현재 세션과 이후 분석에 어떻게 적용할지 정의한다. 개인화의 첫 단계는 사용자별 모델 재학습이 아니라 범위가 명확한 수정 기록을 우선 적용하는 것이다.

## 1. 목표

- 같은 오판을 현재 세션에서 즉시 반복하지 않는다.
- 한 페이지의 수정이 다른 목표·페이지·사용자에게 과도하게 확대되지 않게 한다.
- 알림을 닫거나 무응답한 행동을 정답 라벨로 오해하지 않는다.
- 사용자가 자신의 피드백·파생 캐시·벡터를 삭제할 수 있게 한다.
- 반복 오판을 모델·추출기·정책 개선용 검수 후보로 분류한다.

## 2. 사용자 선택의 의미

| 선택 | 저장 의미 | 관련성 정답인가 | 즉시 동작 |
| --- | --- | --- | --- |
| `목표 관련` | `RELATED` 수정 | 예 | 경고 취소, 현재 구간 재분류 |
| `보조 자료` | `SUPPORTING` 수정 | 예 | 정상 흐름 복귀, 캐시 무효화 |
| `목표와 무관` | `OFF_TASK` 수정 | 예 | 흐름 정책 재평가, 즉시 차단은 금지 |
| `판단하기 어려움` | `UNCERTAIN` 수정 | 예 | 확인 상태 유지, 확정 알림 금지 |
| `계속 보기` | 현재 알림 보류 | 아니요 | 쿨다운 시작, 관련 라벨 유지 |
| `잠시 쉬기` | 세션 일시정지 의도 | 아니요 | Server에 일시정지 요청 |
| 알림 닫기 | UI 닫기 | 아니요 | 짧은 중복 방지 후보 |
| 무응답 | 신호 없음 | 아니요 | 정답·선호로 저장 금지 |

## 3. 피드백 레코드 제안

```json
{
  "feedbackId": "feedback-uuid",
  "goalId": "goal-uuid",
  "goalVersion": 2,
  "sessionId": "session-uuid",
  "runId": "run-uuid",
  "eventId": "event-uuid",
  "contentHash": "sanitized-content-hash",
  "scope": "EXACT_CONTENT",
  "originalLabel": "OFF_TASK",
  "correctedLabel": "SUPPORTING",
  "action": "CORRECT_LABEL",
  "source": "USER_EXPLICIT",
  "feedbackVersion": 1,
  "createdAt": "2026-09-12T10:05:00Z"
}
```

Server가 인증된 사용자 소유권을 결합한다. AI 입력에는 사용자 ID 대신 Server가 제한한 조회 범위나 불투명 참조를 사용한다.

## 4. 적용 범위

| 범위 | 적용 대상 | 기본 허용 여부 |
| --- | --- | --- |
| `EVENT_ONLY` | 특정 관찰 이벤트 한 건 | 허용 |
| `EXACT_CONTENT` | 같은 목표 버전과 정제 콘텐츠 해시 | 기본값 후보 |
| `PAGE_RESOURCE` | 동일한 안전한 페이지·영상·문서 ID | 사용자가 범위를 확인한 경우 |
| `GOAL_TOPIC_PAIR` | 같은 목표와 제한된 주제 조합 | 후속 검토 |
| `DOMAIN_WIDE` | 한 Domain 전체 | 기본 금지 |
| `GLOBAL` | 모든 목표·사이트 | 금지 |

적용 범위가 넓어질수록 사용자에게 영향을 설명하고 명시적으로 확인받아야 한다. URL 쿼리나 전체 원문을 범위 키로 저장하지 않는다.

## 5. 우선순위

판정 시 다음 순서를 제안한다.

1. 제외·개인정보·권한 정책
2. 사용자의 현재 명시적 선택
3. 같은 이벤트의 최신 수정
4. 같은 목표 버전·정제 콘텐츠의 정확 일치 피드백
5. 팀이 검수한 정책 규칙
6. 현재 버전과 일치하는 분석 캐시
7. 규칙·임베딩·LLM 또는 Agent 결과
8. 후속 단계의 유사 사례 참고

개인화가 제외 정책을 해제하거나 민감 페이지 수집을 허용할 수 없다.

## 6. 현재 세션 반영

사용자가 판정을 수정하면 한 트랜잭션 또는 실패 시 복구 가능한 작업으로 다음을 수행한다.

1. 피드백 소유권과 대상 이벤트를 검증한다.
2. 원래 판정과 최신 `feedbackVersion`을 확인한다.
3. 수정 레코드를 저장한다.
4. 대상 구간의 관련성·시간 집계 재계산을 요청한다.
5. 관련 캐시와 대기 중 알림을 무효화한다.
6. 현재 UI에 수정된 상태를 반환한다.
7. 필요하면 해당 회차 노트를 `REGENERATION_REQUIRED`로 표시한다.

일부 단계가 실패했는데 성공으로 표시하지 않는다. 저장은 성공했지만 재집계가 지연되면 `APPLIED_PENDING_RECALCULATION`처럼 처리 상태를 분리하는 안을 검토한다.

## 7. 캐시 무효화

피드백 적용 키에는 다음을 구분한다.

```text
user scope
+ goalId / goalVersion
+ content hash or approved resource reference
+ feedback scope
+ feedback version
```

무효화 대상:

- 관련성 결과 캐시
- 흐름 상태와 대기 알림
- 같은 범위의 Agent Checkpoint
- 집계 결과와 해당 회차 노트
- 후속 유사 피드백 인덱스

정확히 일치하지 않는 목표·콘텐츠의 캐시를 무조건 전체 삭제하지 않는다.

## 8. 수정·철회·충돌

- 피드백을 덮어쓰지 않고 버전을 증가시켜 변경 이력을 구분한다.
- 사용자는 수정 또는 철회할 수 있다.
- 같은 대상에 여러 기기에서 수정이 도착하면 Server가 버전 충돌을 검출한다.
- 철회 뒤 이전 AI 판정을 자동으로 정답으로 복구하지 않고 재분석 필요 상태로 전환한다.
- 목표 버전이 달라지면 과거 피드백은 자동 적용하지 않고 호환 여부를 다시 평가한다.
- 콘텐츠 해시가 바뀌면 페이지 제목이 같아도 정확 일치로 보지 않는다.

## 9. 유사 피드백 검색

유사 검색은 후속 기능이다. 정확 일치 피드백이 부족하고 평가로 이점이 확인된 경우에만 도입한다.

### 9.1 후보 데이터

- 사용자 본인의 검증된 수정
- 목표와 콘텐츠의 민감정보 없는 짧은 표현
- 수정 라벨과 적용 범위
- 모델·추출기·피드백 버전

### 9.2 제한

- 기본은 사용자 본인 범위다.
- Top-K와 최소 유사도는 평가 후 설정으로 관리한다.
- 유사 사례는 참고 근거이며 현재 정답을 자동 확정하지 않는다.
- 한 사례를 Domain 전체 허용 규칙으로 일반화하지 않는다.
- pgvector 도입 여부, 실행 위치와 삭제 전파를 먼저 합의한다.
- 실제 사용자 원문을 Vector Store에 넣지 않는다.

## 10. 반복 오판 개선

다음은 개발자 검토 후보가 될 수 있다.

- 같은 수정 뒤 동일 범위에서 재오판
- 높은 Confidence의 명백한 사용자 수정
- 특정 페이지 유형·언어·추출기에서 반복되는 실패
- `SUPPORTING`을 `OFF_TASK`로 자주 분류하는 패턴
- 사용자 수정 직후 오래된 알림이 발생한 사례

검토 데이터는 목표 요약, 콘텐츠 유형, 원래·수정 라벨, 버전과 오류 코드만 기본 포함한다. 원문이나 캡처는 별도 동의 없이 제출하지 않는다. 검수된 사례만 평가 세트에 추가한다.

## 11. 삭제와 개인화 초기화

사용자 삭제 요청은 다음에 전파한다.

- 피드백 레코드와 변경 이력의 허용 범위
- 관련성·흐름 캐시
- 텍스트·시각 임베딩과 Vector Store 참조
- Agent Checkpoint
- 재분류된 집계와 노트 파생 결과
- 비동기 재집계·재생성 Queue

삭제 중인 데이터를 Worker가 다시 생성하지 않도록 삭제 버전이나 Tombstone을 확인한다. 백업·감사 로그의 처리 기간은 개인정보 정책에서 확정한다.

## 12. 보안과 악용 방지

- Client가 보낸 `userId`를 소유권 근거로 사용하지 않는다.
- 피드백 API는 대상 목표·회차·이벤트가 현재 사용자 소유인지 검증한다.
- 자유 입력 메모는 페이지 콘텐츠와 같은 비신뢰 데이터로 처리한다.
- 수정 라벨 외의 모델·정책 설정을 사용자가 임의로 바꾸지 못하게 한다.
- 대량 피드백 요청은 Rate Limit과 멱등 키로 제한한다.
- 한 사용자의 피드백이 다른 사용자 검색 결과에 노출되지 않게 한다.

## 13. 관측 지표

- 라벨별 명시적 수정 수와 수정률
- 같은 범위 재오판 비율
- 수정 반영과 알림 취소 지연 P50·P95
- 피드백 적용 범위별 적중·거절 수
- 목표 버전·콘텐츠 해시 불일치 수
- 재집계·노트 재생성 성공·실패 수
- 삭제 전파 완료·실패 수

알림 닫기율과 무응답률을 모델 정확도로 해석하지 않는다.

## 14. 검증 시나리오

- `보조 자료` 수정 직후 경고가 취소되고 같은 페이지에 재알림이 없다.
- 같은 페이지라도 다른 목표에는 피드백이 자동 적용되지 않는다.
- 목표 버전 변경 뒤 과거 피드백을 정확 일치로 사용하지 않는다.
- `계속 보기`, 닫기, 무응답이 관련성 정답으로 저장되지 않는다.
- 피드백 충돌에서 마지막 요청이 조용히 이전 값을 덮어쓰지 않는다.
- 다른 사용자의 피드백을 조회·수정·삭제할 수 없다.
- 피드백 철회 후 해당 구간과 노트가 재평가된다.
- 삭제 요청 뒤 캐시·벡터·Checkpoint·Queue에서 참조가 남지 않는다.
- 유사 검색 실패가 기본 관련성 분석을 막지 않는다.

## 15. 팀 합의 필요

- 기본 피드백 범위와 사용자가 선택할 수 있는 범위
- 피드백 수정·철회 기간과 감사 이력
- 집계·노트 재생성의 동기·비동기 처리
- 목표 버전 변경 시 피드백 승계 조건
- 유사 피드백 검색과 pgvector 도입 시점
- 반복 오판 검토 데이터의 사용자 고지·동의 범위

# Frontend 테스트 전략

## 테스트 단계

| 단계 | 대상 | 예시 |
| --- | --- | --- |
| 정적 검사 | TypeScript, ESLint | 타입 오류, 사용하지 않는 값 |
| 단위 테스트 | 순수 함수와 상태 계산 | 남은 시간, 제외 도메인 판별 |
| 컴포넌트 테스트 | 사용자 동작과 UI 상태 | 일시정지 버튼, 오류 안내 |
| 통합 테스트 | API·IPC·Chrome Message 연결 | 세션 응답 후 화면 갱신 |
| 수동/E2E | 실제 macOS와 Chrome 흐름 | 권한 거부, 재실행, Worker 재시작 |

## 기능별 필수 시나리오

- 정상 흐름
- 로딩과 중복 입력
- 빈 데이터
- 잘못된 응답
- 네트워크 끊김과 재연결
- 권한 허용과 거부
- 앱 또는 Popup 재실행 후 상태 복구
- 분석 제외 앱과 도메인

## 기본 검증 명령

```bash
pnpm lint
pnpm build:desktop
pnpm build:extension
```

## 테스트 도구 결정 규칙

- 현재 자동 테스트 도구는 확정하지 않는다.
- 단위·컴포넌트·E2E 중 먼저 필요한 범위를 사용자와 대화해 결정한다.
- 후보 도구의 학습 난이도, Electron·Extension 지원, 실행 속도를 비교한다.
- 사용자가 선택을 확인한 뒤 의존성 설치와 초기 설정을 진행한다.
- AI가 테스트 라이브러리를 임의로 설치하거나 여러 도구를 한꺼번에 추가하지 않는다.

## 결과 기록

- 새 기능이 완료되면 대상 앱의 `docs/features/기능명-REPORT.md`에 결과를 기록한다.
- 단순 버그 수정에는 별도 REPORT를 작성하지 않는다.
- 실패한 테스트를 삭제해서 통과시키지 않는다.
- 자동화하지 못한 시나리오는 수동 테스트 항목과 환경을 남긴다.
- UI 변경은 PR에 실행 화면 또는 스크린샷을 첨부한다.

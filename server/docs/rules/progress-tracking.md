# 진행 상태 추적 & 동시 진행 제한

`server/docs/rules/branch-workflow.md`를 따라 작업할 때 지키는 두 가지 운영 규칙 — "한 번에 하나의 기능만 진행한다"와 "진행 상태를 GitHub Issue로 외부화한다" — 를 다룬다.

## 한 번에 하나의 기능만 (한 Issue, 한 Branch)

- "Issue 1개 ↔ Branch 1개 ↔ 기능 1개"만 동시에 진행한다.
- 진행 중인 Issue(0~11단계 중 어느 단계든)가 끝나기 전에는, 다른 기능 요청이 들어와도 새 Issue의 기획서 작성·브랜치 생성·구현을 시작하지 않는다.
- 새 기능 요청이 들어오면: 진행 중인 Issue가 있다는 것을 알리고, **Issue 생성 자체도 사전 승인 대상이므로** 먼저 "Issue만 만들어 백로그에 남겨둘지" 확인받은 뒤 기획서 작성은 현재 Issue가 끝난 뒤로 미룬다.
- ⚠️ "이런 기능도 나중에 필요할 것 같다"처럼 현재 Issue의 설계 판단을 돕기 위한 맥락 설명은 Issue 생성 대상이 아니다. 명시적으로 "Issue로 만들어줘"라고 하거나 누가 봐도 독립된 기능 요청일 때만 백로그 Issue를 만든다. 애매하면 먼저 "이거 Issue로 만들어둘까요?"라고 물어본다.
- QA 중 발견된 버그는 새 Issue를 파지 않고 같은 브랜치에서 고친다. 새 Issue는 ① 머지 후 발견된 회귀, ② 기획서 범위 밖의 스코프 크립, 이 두 경우에만 만든다.

## 진행 상태 추적 (외부화)

- 기억이 아니라 **Issue 상태**로 진행 단계를 검증한다. Issue를 생성할 때 본문에 0~11단계 체크박스를 전부 포함시키고, 각 단계가 끝날 때마다 그 Issue에서 해당 체크박스를 갱신한다.
- 세션이 끊기거나 새로 시작하는 경우, 진행 중인 Issue가 있으면 그 Issue의 체크박스 상태를 먼저 읽어서 어디까지 진행됐는지 확인한 뒤 이어간다. 대화 기록에 의존하지 않는다.
- 0단계에서, 직전에 닫힌 Issue가 있다면 그 Issue의 문서 반영 단계(Notion 갱신 등)가 실제로 완료됐는지 확인한다. 안 됐으면 새 Issue 착수보다 먼저 그것부터 마무리한다.

## 새 기능 요청 처리 순서

1. 진행 중인 Issue가 있는지 확인한다.
2. 있으면: 이 사실을 알리고, 새 요청을 Issue로 등록할지 확인받는다(백로그).
3. 없으면: `branch-workflow.md` 1단계(Issue 생성)부터 정상 진행한다 — 단, Issue·Branch·PR 생성은 각 단계에서 실행 전 승인을 받는다.

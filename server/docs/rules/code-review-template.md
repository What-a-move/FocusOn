# 코드 리뷰 결과 문서 템플릿

`server/docs/rules/branch-workflow.md` 9단계(코드 리뷰) 결과를 문서화할 때 이 형식을 따른다. 파일 위치: `server/docs/features/{기능명}-code-review.md` (QA 결과 `{기능명}-QA.md`와 분리한다 — 코드 리뷰는 구현 직후, QA는 그다음 단계라 시점이 다르고, 파일이 섞이면 정적 분석으로 찾은 것과 실제 동작 검증으로 찾은 것이 뒤섞여 가시성이 떨어진다).

## 형식 규칙

- **정렬**: 발견 사항은 심각도 내림차순(Critical → High → Medium → Low)으로 정렬하고, 문서 전체에서 하나의 연속된 번호를 매긴다.
- **심각도 표시**: 🔴 Critical, 🟠 High, 🟡 Medium, 🟢 Low — 제목 줄에 번호와 함께 붙인다.
- **각 항목 구성**:
  - 제목: `N. {이모지} {심각도} — 한 줄 요약`
  - **문제**: 무엇이 왜 문제인지 구체적으로 쓴다 — 재현 시나리오, 영향 범위(어떤 요청·데이터에서 발생하는지), 관련 코드 위치(`file:line`)를 포함한다. "~할 수도 있음" 수준으로 뭉뚱그리지 않는다.
  - **해결 방안**: 최소 2가지 이상 제시한다. 각 방안의 장단점(비용, 부작용, 이 프로젝트 컨벤션과의 정합성)을 같이 적어 비교할 수 있게 한다.
- 발견 사항이 전혀 없으면 "Critical/High/Medium/Low 없음"이라고 명시하고, 무엇을 확인했는지(리뷰 범위·방법)를 남긴다.

## 예시

### 1. 🟡 Medium — `GET /api/v1/study-sessions/active`의 만료 세션 처리가 통합 테스트로 커버되지 않음

**문제**: `StudySessionServiceTest`는 정상 조회만 확인한다. `endedAt`이 지난 세션을 다시 활성 세션으로 조회했을 때의 동작(404 반환 여부)은 어떤 테스트로도 검증되지 않는다. `StudySessionController:42`에서 상태 필터링 없이 최신 세션을 그대로 반환하고 있어, 실제로는 종료된 세션이 활성 세션으로 잘못 반환될 수 있다.

**해결 방안**:
1. `status = IN_PROGRESS` 조건을 Repository 쿼리에 추가하고 테스트를 작성한다 — 가장 확실하지만 기존 쿼리 재사용 여부를 확인해야 한다.
2. 이번 범위에서 제외하고 QA 단계에서 수동 재현 후 별도 Issue로 분리한다 — 비용은 낮지만 회귀가 생겨도 자동으로 잡히지 않는다.

## 반영 시점

- 코드 리뷰 직후(9단계)에 작성한다. QA(10단계)를 시작하기 전에 이 파일이 먼저 있어야 한다.

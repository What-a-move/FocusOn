# 코드 리뷰 컨텍스트 격리 규칙

`server/docs/rules/branch-workflow.md` 9단계(코드 리뷰)에서 리뷰를 어떻게 진행하는지 다룬다. 리뷰 결과를 어떤 형식으로 남기는지는 `code-review-template.md`를 따로 참고한다 — 이 문서는 "누가 어떻게 리뷰하는가", 그 문서는 "리뷰 결과를 어떻게 기록하는가"로 대상이 다르다.

## 왜 구현자가 직접 리뷰하지 않는가

기능 구현이 끝나면 QA 전에 diff를 리뷰한다. 구현한 사람이 스스로 검토하면 자신이 만든 가정과 맥락을 그대로 가지고 보게 되어 놓치는 부분이 생긴다. 구현 맥락이 없는 별도 시점·별도 관점에서 diff만 보고 독립적으로 점검한다(AI 에이전트로 작업할 경우, 구현에 사용한 대화와 별개의 새 세션·에이전트에게 리뷰를 맡긴다).

## 컨텍스트 격리 방법

- 리뷰자에게는 diff, 관련 기획서(`{기능명}-PLAN.md`), 이 저장소의 컨벤션 문서(`server/docs/rules/code-style.md`, `docs/API_CONTRACT.md`, `server/docs/DEVELOPMENT_RULES.md`)만 전달한다.
- 구현 과정의 대화 기록·추론·가정은 넘기지 않는다. 구현자의 편향을 그대로 물려받으면 "독립 리뷰"라는 목적이 무너진다.
- AI 에이전트로 리뷰할 경우 구현에 쓴 세션과 분리된 새 세션/에이전트를 사용한다.

## 확인 범위

- 기획서 범위를 벗어난 변경이 없는가.
- 기존 컨벤션(코드 스타일, ErrorCode, 응답 포맷, 계층 분리)을 따랐는가 — `server/docs/DEVELOPMENT_RULES.md` BE-001~BE-005 기준.
- 인증·인가 처리가 빠지지 않았는가.
- 로그에 민감 정보(토큰, 비밀번호, 원본 화면·카메라 데이터)가 남지 않는가 — `docs/DATA_PRIVACY.md` 기준.

## 결과 문서화

결과는 QA(10단계)와 합치지 않고 별도 파일로 즉시 문서화한다: `server/docs/features/{기능명}-code-review.md`. 형식·작성 규칙은 `code-review-template.md`를 따른다.
